# Changelog

All notable changes to DA11Y.md. The shared blocks track A11Y.md, and each entry states the A11Y.md version it compiles from.

## [0.2.0] — unreleased

Compiled from A11Y.md 2.5.0, commit `9fb9a02`.

- **The design system changes only with the person's permission.** Section 2 says it once: a component, its description or its set's, a variable, a style and the library's guidelines are written only when the person allows it. A request to create or change the design system is that permission, for what it asks. Evaluating, analyzing and preparing the handoff are not, and what the agent would change there goes to the person as a warning or a suggestion. Section 6 adds the anti-pattern. Origin: the protocol asked for authorization before fixing, but said nothing of the descriptions and guidelines that Section 2.2 asks the agent to write when it builds a design system.
- **The handoff suggests the descriptions it needs, and says where they go.** When the description of a component or of its set does not say the behavior the reading and the touch areas need, the handoff page gets a card per suggestion: in the set's description when it holds for every variant, in the component's when it holds for one variant only, or in the library's accessibility guidelines when it holds for more than one component. The agent does not write it. `handoff.js` takes `descriptions` and draws them in a fourth section, keeps a card a person decided, and refuses a description for a node that is not an instance or a set description for a component without a set. Origin: in a field test, a card's set description that did not say what was tappable became an open question, and a rewritten one that said so explicitly settled the reading, with no change to the protocol.

## [0.1.0] — 2026-10-21

Compiled from A11Y.md 2.5.0, commit `9fb9a02`.

- **First edition, in English and Portuguese.** The design edition of A11Y.md for whoever designs interfaces in design software, people and agents alike. Principle Zero, the compliance profiles and the severity model are compiled from A11Y.md and never edited here.
- **Section 2, "What already exists comes first".** The agent looks up the library and the prior rules, applies them as they are, evaluates the result, warns about every prior decision that affects accessibility and fixes only with explicit authorization. A WCAG failure the person decides not to fix becomes an `EXCEPTIONS.md` entry. Origin: a pilot with the Figma agent on a real corporate library, where the agent, following A11Y.md, replaced the library's brand colors and a component's border without any accessibility reason and without saying so.
- **Evidence as native annotations.** Each report becomes a Figma annotation in the Accessibility category on the evaluated frame. Origin: in the same pilot, the report and the decisions stayed in the chat, which never reaches the developer.
- **Section 4, "the agent proposes, the person decides".** Reading order, headings, accessible names, alternative text, regions, announcements and language are worked out by the agent. What follows from the design's structure goes into the report as a requirement for development; a choice the design does not settle becomes a `Your decision · agent proposal` annotation, which the person decides.
- **Section 2.2, the context layer for agents.** When the task creates or changes a design system, the agent also delivers the description with aliases, the accessibility contract as data, the anatomy in reading order and a library alias map. The practice follows Meta's Astryx.
- **27 component guides, `references/figma-*.md`.** One per A11Y.md guide with something to draw, each translating that guide into Figma nodes: anatomy, required states, what to measure from the properties, what becomes an annotation, the context layer for the design system, anti-patterns and what stays for code. The Section 7 map links only these guides. The first version of the map sent the design agent to A11Y.md's guides, written for code, and left the translation to it. Measured, a third of those guides is code or keyboard and screen reader scenarios, and none of them names a node, a property or a variant. The one direct link left is the profile guide, because choosing a profile is the same decision in design and code. Each guide was written from the pinned source and reviewed by an agent that did not write it.
- **Section 2, step 5: the defect is fixed where it lives.** A defect of use (variant, override, composition) is fixed in the file with authorization. A defect of the library component itself is never fixed in the file that uses it, because that is an override in disguise: it gets a `Design system error` annotation, is routed to the library and fixed there. Origin: Section 2 said "fix with authorization" and Section 5 said "routed to the library", and the two contradicted each other.
- **Section 5: the report leaves the file.** The annotation on the frame is short (status, date, versions, counts, where the full report is). The full report is `REPORT.md` from this project's template, with `A11Y-DECISIONS.md` and `EXCEPTIONS.md` entries in A11Y.md's formats, delivered with the design. Those files are what the coding agent reads under A11Y.md's *Decision Memory*. Origin: DA11Y.md left evidence as Figma annotations, and A11Y.md never reads annotations, so the design's decisions reached nobody. The A11Y.md core does not change.
- **Section 5: ready for development is a gate.** A section or frame is marked ready (`devStatus`) only with a report at CONDITIONAL or better, no suggestion unconfirmed and no WCAG failure outside `EXCEPTIONS.md`.
- **Section 2.1: compute from the token values, and the person confirms in Figma's own checker.** The agent computes every pair by the WCAG formula on the resolved token values, ratio truncated. When a pair fails, it asks the person to check the same pair in Figma's contrast check in the color picker, which no API exposes to the agent, and never to use its auto-correct, which changes the color. `tools/measure.js` stays in the repository as an optional tool for whoever runs plugins. Origin: asking the Figma agent to run the script proved impractical.
- **Section 2.1: a fallback for screens.** When the annotation tool is unavailable, a component uses its description; a screen uses a `TEXT` layer named `A11Y report` in a `FRAME` of the same name next to it. The earlier fallback covered components only.
- **Section 1: severity on the canvas as a table**, one row per level, since the compiled examples are about keyboard and focus, which the canvas does not show.
- **Section 6 keeps only canvas behaviors.** Placeholder as label, state by color alone and the scrim were duplicates of Section 3. Added: a library defect fixed in the consuming file, a `GROUP` for anything interactive, and marking ready for development without the gate.
- **The Figma edition.** The file says so: the rules would hold in any design tool, the guides are written in Figma's nodes and properties.
- **`templates/REPORT.md`**, the design accessibility report, in both languages.
- **`tools/compile.py` writes the pinned A11Y.md commit** into every edition, guide and template, so a version bump edits `upstream/UPSTREAM.md` only. It also checks the templates' parity between languages and the links to templates and tools.
- **Section 3, targets and focus by profile.** The touch target states each profile's minimum (SC 2.5.8 under Standard, SC 2.5.5 under Shield) and the criteria's exceptions, including the equivalent target. Below the House Rule is a finding to report, never a WCAG failure. Under Shield, SC 2.4.13 applies to focus: 3:1 between the Focus and Default variants. Section 0.1 states that a web screen's unit is the CSS pixel, and that the platforms' 44 pt and 48 dp meet the House Rule under Standard, while 48 is advised under Shield. These rules are written once in the core, which is always loaded, instead of in each guide.
- **Always loaded, loaded on demand.** Library guidelines go to the agent on every prompt and are capped at 200 KB, so only this file and `figma-nodes.md` (about 35 KB) are attached. The guides are opened by link, one row at a time.
- **`references/figma-nodes.md`.** Figma node types, property blocks, annotations, measurements and prototyping, from `@figma/plugin-typings` 1.141.0 and `figma/rest-api-spec` 0.44.0.
- **`tools/compile.py`.** Compiles the shared blocks in both languages and fails on a block that diverges from the pinned source, a number with no ground in A11Y.md, a guide outside A11Y.md's map, an A11Y.md guide left out of the Section 7 map with no recorded reason, or a structural difference between the languages. The same checks run on this project's own guides, whose numbers are grounded in the core or in the pinned A11Y.md guides they translate, and every pinned file must match its sha256 in `upstream/UPSTREAM.md`. Every guide and template is a full link, never a bare or relative path: A11Y.md's at the pinned commit, this project's at the version tag, written by the script. The check also fails when an A11Y.md guide has no translation, no direct link and no recorded reason to stay out of the map.
- **Quick start by link.** The README leads with a rule that points the Figma agent at the core by URL, the way A11Y.md works and the way the pilot ran. Library guidelines become an option, marked as not yet tested: since they accept uploaded files only, `guidelines/` ships a small ready-made file in each language that carries the same rule, so the core stays a single source. Origin: the first README asked for attached files because the repository was private.
- **Links at `main` while the version is a draft.** `tools/compile.py` writes this project's links at `main` while the CHANGELOG marks the version unreleased, and at the version's tag once it is released. Origin: every link pointed at the tag `v0.1.0`, which did not exist, so an agent reading the core by URL got a 404 on `figma-nodes.md`, on every guide and on every template.
- **Section 5: a short annotation in a fixed format, and one report per evaluated set.** Each evaluated frame gets one annotation with its own counts: the status first, then contrast pairs measured and failing, states missing, suggestions awaiting confirmation and library defects, a blank line between blocks, the place of the full report, and the versions last. No date, no hex values, no token names, no recommendations, no caveats. The full report is one per evaluated set (the screen, the flow or the section), and an agent that cannot create files delivers it in the chat for the person to save as `REPORT.md`. Section 4 asks for one subject per annotation, on the node it concerns, and only what each screen has. A library defect is annotated on the evaluated component, once per set, and the agent never annotates or edits the library's file. Origin: a field test on a seven-frame sign-up flow over a real corporate library left 14 frame-level annotations of about 1,000 to 1,800 characters each, with the whole report inside them and the same library findings repeated on every screen. Figma sections do not accept annotations.
- **Every annotation asks for an action, and its first line names the type.** `Your decision · agent proposal` for a choice the design does not settle, which becomes `Decided by <name>`; `Fix here` for a defect of use in this file; `Design system error` for a defect of the library's component, token or style, routed to whoever maintains it. What passed and what follows from the structure (regions from layer names, the heading from the text style, autofill from the field type) go into the report as requirements for development, not onto the canvas. The frame annotation counts the three types and says `Nothing to do on this screen` when all are zero. These replace the `Agent suggestion — confirm` status and the `Library defect` label in the core, the 27 guides and the report template. Origin: in the field test, the designer could not tell from the annotations what to do with each one.
- **Annotating binds whoever evaluates, not only whoever designs.** A statement right before Principle Zero says designing and evaluating end the same way, with the annotations written in the file, for creating, editing, analyzing and reviewing, and that annotating needs no authorization. The Section 2.1 contract now binds "any agent designing or evaluating", and so do the introduction, the instruction to read `figma-nodes.md` first and the Section 7 map. The `Fix here` and `Design system error` annotations move from Section 2 step 5, "fix only with explicit authorization", to step 4, "warn". Section 6 says the same of leaving the evidence only in the chat. Origin: asked twice for an accessibility analysis of six screens over a real corporate library, the Figma agent cited the per-screen annotation the core requires and skipped it, as "a change beyond the analysis requested". The core bound the annotation to "any agent designing" and stated it inside the step that asks for authorization.
- **`figma-nodes.md`: writing `annotations` replaces the whole list.** The agent reads what the node already has and writes it all back, the new one last, so no one's annotation disappears. The note that the Figma agent might not write annotations is replaced by the field result: it does, in Figma Design. Origin: in the same review, a plugin that sets the list overwrote the first of two annotations on one node.
- **The prototype is optional.** Connecting screens in the prototype is the designer's choice, not an accessibility requirement: a screen on its own is evaluated by what it shows. When there is a prototype, its reactions are evidence (a hover-only action, a toast that disappears); when there is none, nothing fails for it. Section 0 drops "if the task does not complete in the prototype, the design is broken", Section 1 drops it from CRITICAL, and every guide line that required a reaction now asks for the drawn control or screen instead, such as a modal's Close, a carousel's pause or a Move menu. A reaction that exists still counts when it shows a barrier, such as a hover-only action. Origin: the same review flagged six unconnected screens as a critical failure, and the designer running the review pointed out that a single screen of a flow would always be born wrong.
- **Section 5: each annotation type has its own category, and the evaluation ends in the file.** The agent reads the file's annotation categories and creates the missing ones: `Accessibility` for the frame annotation, and `Your decision`, `Fix here` and `Design system error` for the action annotations, each with a fixed color, so each person can filter by what they have to do. The first line still names the type, and a tool that cannot create categories falls back to `Accessibility`. An evaluation, an analysis or a review ends only when the annotations are written and read back against the frame's counts; offering to annotate later is not a delivery. Origin: the same review, where the Figma agent ended with an offer to annotate.
- **The activation rule covers evaluating.** "When designing or evaluating flows, screens or components…", in the README and in the ready-made guidelines. Origin: the same review was an analysis, and the rule named designing only.
- **The color guide follows the annotation format.** `figma-visual-perception.md` was left out of the change that gave every annotation a type. It still put the pair table in the frame annotation, called a failing pair a suggestion, and sent the palette's pair matrix to an annotation and to the `REPORT.md` of A11Y.md, whose §1 is a code checklist. Now the pairs go to this project's report, a failing pair gets a `Design system error` or `Fix here` annotation on its own node, and the palette's matrix goes to `A11Y-DECISIONS.md` only. Origin: reading the accessibility skills shared in the Figma Community side by side with the guides, in October 2026.
- **Reading color in Figma, precisely.** Text whose ranges differ returns `figma.mixed` for `fills`, `fontSize` and `fontWeight`, and is read per range, each range a pair. Transparency lives in each paint's `opacity`, because a `SOLID` color has no alpha, as well as in the node's and each ancestor's, and a color read from a variable carries it in its `a` channel. A gradient is not measured at its stops only, because under sRGB interpolation, CSS's default, the color between two stops can have less contrast than both. Black text over a red to green (#008000) gradient measures 5.25:1 and 4.06:1 at the stops and 2.63:1 halfway. Another mode is measured by reading the variable's value in that mode, never by switching the evaluated frame's mode, and `tools/measure.js` no longer says to switch it. `figma-nodes.md` adds `getMainComponentAsync()`, `remote`, `valuesByMode` and `valuesByModeForCollectionAsync`, checked against `@figma/plugin-typings` 1.141.0. Origin: a design system documentation skill in the Figma Community multiplies color alpha by paint opacity and resolves aliases mode by mode, and a component audit skill reads styles and main components this way.
- **Section 2: brand assets are prior decisions.** The brand assets the person points to join the library and the rules on record. Their values are read from the nodes themselves and go in exactly, never approximated. With a brand and no library, the brand's values are the prior decision. Origin: Section 2 protected the brand only when it came from a library, and said a file without one had nothing to preserve. In the pilot, the agent had replaced the brand's colors. A design system generator in the Figma Community starts by extracting the exact brand values, never similar ones.
- **Section 2: where a component comes from decides where it is fixed.** A library component comes from outside the evaluated file (`remote`). A local component gets `Fix here` on its main component and is fixed there, never on the instance. When the evaluated file is the library itself, the `Design system error` goes on the main component, where the authorized fix is made. A library defect is annotated once per failing variant, not once per component, because variants of one component pass and fail separately. Origin: the routing in Section 2 depended on telling a library component from a local one, and the text did not say how. Read literally, "the agent never annotates the library's file" also forbade evaluating a library. A review skill in the Figma Community warns that one chip variant fails while another passes.
- **Section 5: what a new evaluation does with the annotations already there.** The agent measures again, removes each `Fix here` and `Design system error` whose defect is gone, updates or removes each undecided proposal and rewrites the frame annotation. It never touches `Decided by <name>`, nor any annotation that has no type and not the frame format. Origin: Section 5 said a new evaluation updates instead of stacking, but not how. Two skills in the Figma Community, by different authors, reach the same design: mark what you write, and remove only your own.
- **The Figma agent, measured in the field.** `figma-nodes.md` records what tests on 2026-10-16 showed about the Figma agent. It runs Plugin API code. In its code, `figma.currentPage.selection` is empty, and the agent sees the person's selection in its own context, by id and type, without the name. `figma.skipInvisibleInstanceChildren` is on, so `children`, `findAll` and `getNodeByIdAsync` skip hidden layers inside instances. It reads a script by link and runs it. Origin: asked to run `measure.js` on a section with seven screens, the agent returned a report of zeros. A short snippet showed that the selection in its code was empty, and finding the node by id fixed it.
- **`measure.js` takes ids and never returns an empty report.** It accepts node ids, an id copied from a link, or nodes. With nothing to measure, it stops with an error that explains the agent's empty selection. Its output lists the measured scope and any id not found. It reads a component with `getMainComponentAsync()`, and a variant's set name now counts when it looks for targets. It counts a color variable's alpha, once when the paint's opacity carries the same value, and the opacity of every layer between a text or a border and its background. A background under a translucent layer goes to `notMeasured`. Origin: in the same test, an empty selection produced a report of zeros that read like a clean screen. The color guide already asked for the variable's alpha and the ancestors' opacity.
- **One annotation per element, short, with the reading order.** Section 5 drops the type written out on the first line for a short format whose start says the type. Each element where a screen reader stops gets one `Your decision` annotation: the order and the element on the first line (`4 · card`), then `🔊` what is read at each stop, `🔇` what is not, `📢` what is announced and `❓` the open choice. A library error is one line, such as `🔴 Library: no Focus state`, and a defect of use is `🟠 Here: …`, with the severity color of Section 1. Measurements, caveats and how to check go into the report. A person decides by adding `✓ <name>`, which replaces `Decided by <name>`. Section 4 puts the reading order on the canvas, numbered, and sends the keyboard focus order to the report. The examples of the 27 guides, the report template and the color guide follow. Origin: on an app screen, the Figma agent wrote 28 annotations, and 19 repeated the same text with another name inside. Each card, its icon and its arrow had separate annotations, with severity, measurements and caveats in every one. Section 4 asked for one subject per annotation, and the brevity rule covered the frame annotation only. The designer asked for the gist, such as 🔇 for a decorative icon, and for the reading order on the element itself.
- **`tools/annotate.js`.** It writes the Section 5 annotations and reads them back. It creates the missing categories and replaces the agent's own annotations from an earlier evaluation, the long format included. It keeps people's annotations and any annotation with a `✓`. It writes the frame annotation from the counts, so the two cannot disagree. Before writing anything, it refuses an item outside the format, a line over 160 characters or an error over two lines. Section 5 points to it, and Section 2.1 points to `measure.js`. Origin: what has broken in the field is writing the annotation list without erasing someone else's, and keeping the frame's counts true.
- **The skill is only the rule.** The README shows how to install DA11Y.md as a Figma agent skill: the name, a description that makes it run without typing `/`, and the activation rule as its instructions. Origin: a draft skill carried the procedure and the annotation code, and duplicated the core. The tests showed that the Figma agent reads the protocol and runs tools by link, and that the description, not the body, makes the skill run.
- **The severity of an error, in color and in text.** A `Fix here` or `Design system error` annotation starts with the severity's circle and its Section 1 name, such as `🔴 CRITICAL · Library: no Focus state`. `annotate.js` refuses an error without the name, or whose color and name disagree. It still replaces the unlabeled short format written earlier the same day. The core, `figma-nodes.md`, the color guide and the READMEs follow. Origin: an independent audit of the project page noted that the severity was shown by color alone, which the protocol forbids for a state. The designer asked for a text label.
- **Section 4 of 13 guides: what goes into the annotation, and what goes into the report.** Each of these guides now splits Section 4 into two groups. What the screen reader reads, announces or skips, and the choices the person makes, go into the element's annotation, in the short format of Section 5. Keyboard keys, focus movement, closing, timing, input type and structure the code must keep go into the report, as requirements for development. No fact, number or rule changed. The guides are autocomplete, charts, consent banners, date picker, drag and drop, forms, maps, media, modals, navigation, tabs and accordion, toasts and tooltips. Origin: after the short format, these guides still listed keyboard and behavior as annotation content.
- **One stop per 🔊 line, numbered.** A reading annotation with more than one stop takes a range on its first line. Each `🔊` line starts with its number, one stop per line: `4–8 · request status`, then `4) 🔊 …` to `8) 🔊 …`. Repeated items that follow one mold, such as each row of a table, fit on one line. `annotate.js` refuses a range whose `🔊` lines do not match it, and a single number with more than one `🔊` line. Twelve guide examples that listed several stops on one line now have one stop per line. Origin: on a real screen, an annotation listed two stops on each `🔊` line, and the designer could not tell which one is read first.
- **Only what is visible.** Section 2.1: a hidden layer, on the node itself or on an ancestor, stays out of the measurements, the reading and the annotations, inside instances too. `annotate.js` refuses a hidden node. `figma-nodes.md` no longer advises turning off `skipInvisibleInstanceChildren` to check states. A state that exists only as a hidden layer is checked through the component's properties. Origin: the designer's instruction after the same test.
- **The platform is stated, and heading levels exist on the web only.** Section 0.1: before evaluating, the agent states whether the screen is web or an iOS or Android app, and which evidence shows it, such as the system's status or navigation bar, iOS or Material components, or the name of the page, file or library. The frame's width does not decide, and with no evidence the agent asks. The platform decides the unit, the target, the annotation's vocabulary and whether the app guide applies. Section 4: on the web a heading carries its level (`🔊 heading H2 "Orders"`), and in an app it is just "heading", because iOS and Android have no levels. The report template gets a Platform field. Origin: the designer asked whether the skill tells web from mobile on its own. It did not: in a field test the agent inferred an app from a Brazilian app standard, silently. A11Y.md already requires identifying the platform first (Platform Awareness). The core's example also gave a heading level to a card taken from an app.
- **The canvas shows only what is read.** The `🔇` mark is gone. A reading annotation is a closed list: what sits inside the element and is not on a `🔊` line is not read, and the person's `✓` confirms the whole list, what was left out included. What the reading leaves out goes into the report with the reason, in a new "Not read" table, and the frame annotation counts it ("Not read — n"). An informative image goes in as `🔊 image "alternative text"`, and a decorative candidate stays off the canvas and goes into the report. The `❓` line is kept for structural choices, such as tabs or navigation. `annotate.js` refuses `🔇` lines and writes the not-read count it receives. The images, media and loading guides follow, and the loading guide's Section 4 splits the annotation from the report, like the other thirteen. Origin: in a field test, the agent classified a map as an informative image and a car photo as an image, and left both as open `❓` questions. The designer asked to show only what is read.
- **The skill in the Figma Community.** The `da11y` skill is published at https://www.figma.com/community/skill/136973/da11y, and the README's quick start begins with it. Creating the skill by hand stays as the alternative.
- **Additional sources.** Magoo, by Marcelo Sales, and Astryx, by Meta, as non-normative references.
- **Two modes, one protocol: the reading goes onto the canvas when asked for.** Section 4: the reading of each element goes onto the canvas when the request is to deliver a designed screen or to annotate the reading. When the request is to evaluate, analyze or review, the reading stays off the canvas: the evaluation delivers the measurements, the errors, the `❓` lines and the frame annotation, and the report carries the reading as a draft. A verdict (a measured fact or a rule) and a proposal (the reading) no longer carry the same weight on the canvas. The frame annotation counts them apart: "Your decisions" counts the annotations with a `❓` still open, and a new line, "Readings to confirm", the reading annotations. Origin: a field test on a mobile screen, evaluated with the published skill. The analysis was good (five real findings, contrast and origin right, hidden layers out), the reading was mostly right, and the part it invented looked authoritative: two attachments became buttons named "Open …" with no control drawn, and the frame said "Your decisions — 14" when four were decisions and the rest were readings to confirm. The market tools reviewed the same day (Stark, axe for Designers, BrowserStack's design toolkit, GitHub's Annotation Toolkit) keep the check and the handoff annotation as two modes, and their AI only suggests until the person accepts.
- **A closed role vocabulary on `🔊` lines.** Section 4: a stop says its role in one of twenty words per language (button, link, heading, field, combobox, checkbox, radio, switch, slider, tab, menu, dialog, modal dialog, list, table, tree, group, navigation, image, map), or no role, in quotes only. `annotate.js` refuses any other word. Repeated stops that follow one mold fit on one line (`🔊 each row: "…"`). Long text goes in by its beginning, with an ellipsis inside the quotes. Origin: the same test mixed "text", "header" and "informative image" as roles, and described a long text ("followed by the full account") instead of quoting it.
- **`❓` for structure and role only, and an error is certain.** Section 4: a `❓` asks what the marks do not say (tabs or navigation, whether a card is a control), never content, product or behavior, which go into the report, and never repeats an error. A `Here:` or `Library:` annotation never depends on an answer; what depends on an answer is a `❓`. The Section 5 example loses its "if the card opens details". One finding per error annotation: a second line continues the first and never starts another severity, and `annotate.js` refuses both. Origin: the same test wrote nine `❓` lines, four about structure and the rest about a date, a value and a product rule; three errors said "if it collapses…" or "if there is an action"; two annotations carried two findings each, so the frame counted four library errors for seven findings.
- **Focus in an app.** Section 3: the library instance that stands for a platform control inherits the system's focus, as `figma-platform-native.md` already said. A missing Focus variant goes into the report, as the requirement to use the system's focus or to design the state, and is not an error. In an app, the 🔴 CRITICAL for a missing Focus applies to a control drawn from scratch. Section 1's table and the Section 2.1 contract say so. Origin: the same test flagged two library buttons as CRITICAL for a missing Focus variant, applying the Section 1 table where the app guide said the control brings its own focus.
- **`figma-platform-native.md`: the status bar and the navigation bar.** The system's status bar stays out of the reading, the measurements and the annotations. The navigation bar is read as Back, then the title as `heading`, then the actions on the right. Section 4 splits into the annotation and the report: focus or announcement on opening (by default the screen title) and the focus of each control go into the report. A name contains the visible text, and a verb the screen does not show does not go into the name. Origin: the same test called the navigation bar's title "text" and the content title "header", and gave the attachments a verb the screen does not show.
- **`figma-images.md`: alternative text that would repeat the text next to it** makes the image a decorative candidate, because the screen reader would say the same thing twice. Section 4 of the core says it in one sentence. Origin: the same test read the map with the address as its alternative text, and the address again on the next stop.
- **The frame annotation says the profile and the platform.** Its last line is `Standard (AA) · app · DA11Y.md 0.1.0 · A11Y.md 2.3.0`, because a ratio that passes under Standard fails under Shield, and whoever builds read "CONDITIONAL" without knowing against what. `annotate.js` requires both. Origin: the same test, where the smallest ratio was 5.51:1, a pass under Standard and a fail under Shield.
- **The report lives in the file.** Section 5: an agent that cannot create files, such as Figma's, writes the full report on a page of the file named `DA11Y — reports`, one `TEXT` per evaluated set, named after the set, and repeats it in the chat for the person to save as `REPORT.md`. A new evaluation of the same set updates the same `TEXT`. `report()` in `annotate.js` does it, and the frame annotation now points to that page. The Section 2.1 fallback for a screen is the same page. Origin: the frame annotation said "Full report in the evaluation chat", a place whoever builds never opens. Stark and BrowserStack keep the report in the file.
- **The `Your decision` category becomes `Proposal`, and the frame says when the reading was not annotated.** The category's name now says what the annotation is, not what it becomes: a proposal of the agent, which the `✓ <name>` turns into a decision. Without the `✓`, whoever builds asks. The frame annotation counts `Open questions` (annotations with a `❓` still open) and `Readings to confirm`; on an evaluation, where the reading is not annotated, the line says `Readings — not annotated` instead of counting zero, because a zero would say nothing is pending. `annotate.js` takes `mode` ("evaluation" or "reading"), refuses a reading annotation in evaluation mode, writes the new category and leaves the old one in the file, empty, for the person to delete. Origin: the designer asked what the decision was, after all, since the annotation is a suggestion the person edits if they want; and whether the modes would produce different annotations. They do not: the same three categories and the same frame, with a different mix, and the frame's zero was the one real gap.
- **Section 4: a component with an action inside is one item.** A card with an Edit button is read as one item with its stops numbered, such as `5–6 · payment`, even when the card itself is not tappable. Origin: in a field test, the agent split a payment card's text and its Edit button into two items, and the designer asked whether they belonged together.
- **Section 3: the 8px between targets applies when either target is small.** The House Rule keeps 44×44 (48×48 under Shield), and asks for 8px between two neighbors only when either is below that size, as A11Y.md puts it for dense UIs with targets under 44px. Targets of that size may touch, like the rows of a list. `measure.js` now reports `houseRule` by size and the spacing apart. Origin: in a field test, list rows 56 tall, touching, became a House Rule finding and a `Fix here` annotation; the edition had dropped the context A11Y.md gives the 8px.
- **"House Rule" is now "A11Y.md rule" ("regra do A11Y.md"), following A11Y.md.** The label marks what A11Y.md requires beyond WCAG at the chosen level, and the old name told whose rule it was only to whoever already knew. "Recommendation" was dropped, since most of these rules are MUST and ABNT NBR 17225 has its own recommendations. The meaning stays: falling short of an A11Y.md rule is a finding, never a WCAG failure. The rename was released in A11Y.md 2.5.0 (fecarrico/A11Y.md#112), and the compiled blocks changed in that name only. Origin: in the handoff cards, "House Rule (44 × 44): below" told the designer neither whose rule it was nor that it goes beyond WCAG.
- **Section 2: a component's description is a prior decision.** Before designing or evaluating, the agent reads the description of each component used and of its variant set, with `DESIGN.md`, the guidelines and the decisions. What a description says about behavior, such as the touch area, is a prior decision, and when the design contradicts it, the doubt becomes a structural question (❓), never a side the agent picks. `measure.js` returns, under `components`, the descriptions of the components it meets. Origin: in a field test, the agent evaluated a card as not tappable, while its variant set's description gave the whole card as the touch area; the protocol named descriptions only for whoever builds a design system (Section 2.2).
- **The canvas keeps only what is fixed in the file, and the rest goes onto two pages.** Section 5: besides the frame annotation, the canvas gets only `Fix here`, each ending with the number of its finding (`· finding 2`). Every finding is numbered once and drawn on the `DA11Y — reports` page, on the edge of a full-size copy of the evaluated screen, beside its card: `Fix here` by severity, then `Design system error` by component, then the `❓`. The handoff, when asked for or when the agent delivers a designed screen, is the `DA11Y — handoff` page: the reading as numbered cards beside a copy of the screen, the touch areas measured against the profile, and each control beside its focus variant from the library. The person writes `✓ <name>`, or the answer to a `❓`, on the card, and a new run keeps it. A tool that cannot draw the pages annotates every type on the canvas, as before. Sections 2.1, 4 and 6, the README and the report template follow. Origin: in runs on real app screens over a real library, the annotations, even short, covered the screen when there were many, and numbered cards beside a copy of the screen already said what is read.
- **`tools/handoff.js` and `tools/report.js`.** They draw the two pages the same way every time: the agent decides the content, and the script places it and measures it in the file. Both follow the screen's design system, its text styles and its color variables, when their pair passes 4.5:1, and fall back to ink and paper when it does not. `report.js` draws the report's Markdown as headings, tables and lists, opens it with the evaluated screens linked to the originals, and rewrites the frame annotation's report line as a link to it. Both replace their own block on a new run and keep every card a person decided. A decided report card whose finding left the new analysis is listed apart. They never change the design.
- **`tools/annotate.js` numbers the findings and leaves the rest to the page.** It writes the frame annotation and the `Fix here` ones, keeps the counts of what went to the page on the screen, so `reread()` still checks the frame, and returns the numbered list `reportPage()` draws. `onPage: false` keeps every annotation on the canvas.
- **`tools/measure.js` never takes a text for a target**, even one named "Button text".
- **The report template numbers the findings.** Sections 5 and 6 open with a `#` column, the same number as on the report page and on the `Fix here` annotation.
- **The Figma tools are built and tested.** `tools/build.py` builds `handoff.js` and `report.js` from `tools/src/`, and `tools/tests/run.js` runs the four tools on a Figma document in memory. CI runs both on every pull request.
